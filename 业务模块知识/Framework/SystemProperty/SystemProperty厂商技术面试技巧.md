# SystemProperty厂商技术面试技巧

## 1. 基础概念类问题

### 1.1 什么是SystemProperty？它的作用是什么？

**回答要点**：
- SystemProperty是Android系统中用于存储和访问系统级属性的键值对存储机制
- 提供全局共享、持久化存储、权限控制等功能
- 主要用于系统配置管理、运行时状态跟踪、跨进程通信等

**扩展回答**：
SystemProperty是Android系统中的核心基础设施，它提供了一个轻量级的键值对存储系统，用于在系统各组件间共享配置信息。SystemProperty的设计目标是解决Android系统中跨进程配置共享的问题，同时通过多层次权限机制保障系统安全。

SystemProperty的主要作用包括：
1. **系统配置管理**：存储硬件信息、系统服务配置、功能开关等
2. **运行时状态管理**：跟踪系统启动状态、USB状态、网络状态等
3. **跨进程通信**：系统服务间通过属性发布状态、同步配置、通知事件
4. **调试与诊断**：提供调试开关、性能监控、故障排查等功能

### 1.2 SystemProperty的存储位置和类型有哪些？

**回答要点**：
- 存储位置：/system/build.prop、/data/property/、内存映射区域
- 类型：只读属性(ro.*)、持久化属性(persist.*)、控制属性(ctl.*)等

**扩展回答**：
SystemProperty根据存储位置和特性可以分为以下几类：

1. **按存储位置分类**：
   - **只读属性**：存储在/system/build.prop等只读分区，系统启动时加载
   - **持久化属性**：存储在/data/property/目录，修改后持久化存储
   - **运行时属性**：仅存储在内存中，系统重启后丢失

2. **按前缀分类**：
   - **ro.**：只读属性，通常存储硬件信息，如ro.product.model
   - **persist.**：持久化属性，修改后会写入/data/property/目录
   - **ctl.**：控制属性，用于启动/停止系统服务
   - **debug.**：调试属性，用于调试和开发
   - **sys.**：系统属性，系统运行时状态
   - **dalvik.vm.**：Dalvik虚拟机相关配置

3. **按访问权限分类**：
   - **公开属性**：所有应用可读写，如debug.*、log.tag.*
   - **系统级属性**：系统应用可读写，如sys.*、persist.*
   - **签名级属性**：需要特定签名，如ro.*、service.*
   - **平台级属性**：需要platform签名，如ctl.*、security.*

### 1.3 SystemProperty的访问流程是怎样的？

**回答要点**：
- Java层：SystemProperties.get/set → JNI → Native层
- Native层：__system_property_get/set → Socket通信 → 属性服务
- 服务端：权限检查 → 属性设置/获取 → 结果返回

**扩展回答**：
SystemProperty的访问流程可以分为客户端和服务端两部分：

**客户端访问流程**：
1. **Java层调用**：应用调用SystemProperties.get()或set()
2. **本地缓存检查**：检查本地缓存，命中则直接返回
3. **JNI层调用**：缓存未命中，调用native方法
4. **Socket通信**：建立与属性服务的Unix Domain Socket连接
5. **发送请求**：发送属性设置/获取请求
6. **接收结果**：接收服务端处理结果
7. **更新缓存**：更新本地缓存，通知变更监听器

**服务端处理流程**：
1. **接收连接**：accept客户端连接
2. **解析请求**：解析属性设置/获取请求
3. **权限检查**：进行SeLinux、签名等多层权限检查
4. **属性操作**：执行属性设置/获取操作
5. **持久化处理**：对persist.属性进行持久化
6. **变更通知**：通知属性变更监听器
7. **返回结果**：返回操作结果给客户端

## 2. 深度技术类问题

### 2.1 SystemProperty的内存映射机制是如何实现的？

**回答要点**：
- 属性区域使用共享内存映射，实现高效访问
- 属性区域包含头部信息、哈希表和属性数据区
- 使用原子操作和序列号机制保证数据一致性

**扩展回答**：
SystemProperty的内存映射机制是其高性能访问的关键，具体实现如下：

1. **属性区域结构**：
```c
struct prop_area {
    uint32_t version;        // 版本号
    uint32_t magic;          // 魔数，用于校验
    uint32_t size;           // 属性区域大小
    uint32_t count;          // 属性数量
    uint32_t hash_table_size;// 哈希表大小
    uint32_t hash_table[0];  // 哈希表
    char data[0];            // 属性数据区
};
```

2. **内存映射过程**：
   - 系统启动时，init进程创建属性区域文件
   - 使用mmap将文件映射到内存空间
   - 所有进程通过相同的映射访问属性区域
   - 属性区域使用原子操作保证并发访问安全

3. **哈希表优化**：
   - 属性名通过哈希函数计算哈希值
   - 哈希表存储属性在数据区的偏移量
   - 支持链式解决哈希冲突
   - 查找时间复杂度接近O(1)

4. **数据一致性保证**：
   - 每个属性有32位序列号
   - 修改属性时原子更新序列号
   - 读取属性时检查序列号一致性
   - 支持属性变更通知机制

### 2.2 SystemProperty的权限控制机制是怎样的？

**回答要点**：
- 多层权限控制：SeLinux、签名权限、UID/GID权限
- SeLinux策略文件定义属性访问权限
- 动态权限调整和审计机制

**扩展回答**：
SystemProperty的权限控制机制是Android安全体系的重要组成部分，采用多层权限控制：

1. **SeLinux权限控制**：
   - SeLinux策略文件(/system/sepolicy/)定义属性访问权限
   - 属性类型定义(property.te)：system_prop、debug_prop等
   - 属性上下文映射(property_contexts)：属性名到安全上下文
   - 权限授予(如system_app.te)：允许特定进程访问特定属性

2. **签名权限检查**：
   - 检查调用应用的签名是否匹配要求
   - platform签名：可访问平台级属性
   - 系统签名：可访问系统级属性
   - 特定签名：可访问特定属性

3. **UID/GID权限检查**：
   - 检查调用进程的UID/GID
   - system UID：可访问系统级属性
   - root UID：可访问所有属性

4. **动态权限调整**：
   - 支持运行时动态调整属性权限
   - 临时权限机制，满足开发调试需求
   - 权限审计机制，追踪异常访问

### 2.3 SystemProperty的性能优化有哪些方法？

**回答要点**：
- 客户端缓存：减少跨进程通信
- 批量访问：减少通信开销
- 内存优化：优化属性区域结构
- 启动优化：预加载关键属性

**扩展回答**：
SystemProperty的性能优化可以从多个维度进行：

1. **客户端缓存优化**：
   - 本地缓存常用属性，减少跨进程通信
   - 分层缓存：热缓存+冷缓存，提高命中率
   - LRU策略管理缓存大小，防止内存占用过高
   - 属性变更通知机制，保证缓存一致性

2. **批量访问优化**：
   - 批量获取多个属性，减少通信次数
   - 合并连续的属性访问请求
   - 异步批量操作，避免阻塞主线程

3. **内存优化**：
   - 属性区域使用共享内存，避免数据拷贝
   - 优化属性数据结构，减少内存占用
   - 内存池管理，减少内存分配开销
   - 属性值压缩，减少内存使用

4. **启动优化**：
   - 预加载关键属性，减少启动时的访问延迟
   - 按优先级分类加载，优先加载关键属性
   - 并行加载非关键属性，提高启动速度

5. **访问路径优化**：
   - 优化属性查找算法，提高查找效率
   - 减少权限检查开销，对频繁访问的属性简化检查
   - 异步权限检查，避免阻塞属性访问

## 3. 实践应用类问题

### 3.1 如何解决SystemProperty的权限问题？

**回答要点**：
- 分析权限拒绝原因：SeLinux、签名、UID/GID
- 解决方案：修改SeLinux策略、调整签名、使用动态权限
- 调试工具：getprop、setprop、权限检查工具

**扩展回答**：
解决SystemProperty权限问题需要系统性的方法：

1. **问题诊断**：
   - 检查错误码：0x18表示权限拒绝
   - 分析日志：查找"permission denied"相关日志
   - 确定权限类型：SeLinux、签名或UID/GID

2. **SeLinux权限问题**：
   - 检查当前进程安全上下文：`ps -Z`
   - 检查属性安全上下文：`ls -Z /dev/socket/property_service`
   - 修改SeLinux策略：添加属性类型和权限规则
   - 重新编译和刷入sepolicy

3. **签名权限问题**：
   - 检查应用签名：使用keytool检查签名信息
   - 使用系统签名：使用platform签名重新签名应用
   - 调整属性权限：降低属性签名要求

4. **UID/GID权限问题**：
   - 检查进程UID/GID：`ps | grep <app_name>`
   - 调整应用UID：将应用安装为系统应用
   - 使用sharedUserId：与系统应用共享UID

5. **动态权限调整**：
   - 临时权限提升：使用动态权限调整接口
   - 权限白名单：将特定应用加入权限白名单
   - 开发模式：在开发版本中放宽权限限制

## 4. 场景设计类问题

### 4.1 设计一个高性能的SystemProperty缓存系统

**回答要点**：
- 缓存策略：LRU、分层缓存、智能预测
- 一致性保证：变更通知、版本控制、过期机制
- 内存管理：大小限制、压缩、内存池

**扩展回答**：
设计一个高性能的SystemProperty缓存系统需要考虑以下方面：

1. **缓存架构设计**：
```java
public class HighPerformancePropertyCache {
    // 分层缓存设计
    private final Map<String, CacheEntry> hotCache;      // 热点缓存
    private final Map<String, CacheEntry> coldCache;     // 冷缓存
    private final Map<String, CacheEntry> persistentCache; // 持久化缓存
    
    // 缓存配置
    private final int hotCacheSize;
    private final int coldCacheSize;
    private final long expireTime;
    
    // 访问统计
    private final Map<String, AccessStats> accessStats;
    
    // 缓存条目
    private static class CacheEntry {
        String value;
        long timestamp;
        int accessCount;
        boolean isDirty;
        String version; // 用于一致性检查
    }
    
    // 访问统计
    private static class AccessStats {
        int totalAccess;
        long lastAccessTime;
        double accessFrequency;
    }
}
```

2. **缓存策略实现**：
   - **热点识别**：根据访问频率和最近访问时间识别热点属性
   - **动态调整**：根据访问模式动态调整缓存大小和内容
   - **预测加载**：基于历史访问模式预测即将访问的属性
   - **智能淘汰**：综合考虑访问频率、时间和大小等因素进行淘汰

3. **一致性保证机制**：
   - **变更通知**：监听属性变更事件，及时更新缓存
   - **版本控制**：为每个缓存条目维护版本号，检测不一致
   - **过期机制**：设置缓存过期时间，定期刷新缓存
   - **验证机制**：定期验证缓存与实际属性的一致性

4. **内存管理优化**：
   - **大小控制**：严格控制缓存大小，防止内存占用过高
   - **压缩存储**：对长属性值进行压缩存储
   - **内存池**：使用内存池减少内存分配开销
   - **分级存储**：根据访问频率分级存储，优化内存使用

struct android_version_features {

const struct android_version_features* detect_android_features() {

        if (version_features[i].api_level == api_level) {
