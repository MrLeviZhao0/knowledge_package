## 常见面试问题及回答策略

### 基础概念类问题

**问题1：Soong和Bazel的主要区别是什么？**

**回答策略：**
- **设计目标**：Soong专为Android设计，Bazel是通用构建工具
- **构建语言**：Soong使用Blueprint，Bazel使用Starlark
- **依赖管理**：Soong基于Android.bp，Bazel基于BUILD文件
- **性能特点**：Soong优化Android构建，Bazel强调可重现性
- **适用场景**：Soong适合Android系统构建，Bazel适合大型跨平台项目

**问题2：为什么Android要从Make迁移到Soong？**

**回答策略：**
- **性能问题**：Make构建速度慢，依赖解析效率低
- **可维护性**：Android.mk文件复杂，难以维护
- **扩展性**：Make扩展困难，难以支持新的构建需求
- **并行构建**：Soong更好的并行构建支持
- **错误检测**：Soong提供更好的编译时错误检测

### 技术实现类问题

**问题3：Soong的构建流程是怎样的？**

**回答策略：**
- **解析阶段**：解析Android.bp文件，生成模块依赖图
- **生成阶段**：根据依赖图生成ninja构建文件
- **执行阶段**：使用ninja执行实际的构建命令
- **关键组件**：Blueprint解析器、依赖分析器、ninja生成器

**问题4：Bazel的沙箱构建机制有什么优势？**

**回答策略：**
- **可重现性**：确保每次构建结果一致
- **隔离性**：避免环境变量和系统状态影响构建
- **安全性**：防止构建过程对系统造成影响
- **缓存友好**：沙箱构建结果更容易缓存和复用
- **并行安全**：多个构建动作可以安全并行执行

### 性能优化类问题

**问题5：如何优化Soong构建性能？**

**回答策略：**
- **增量构建**：使用mm/mma命令只构建变更部分
- **并行构建**：使用-j参数充分利用多核CPU
- **缓存优化**：启用ccache加速C/C++编译
- **模块优化**：合理拆分模块，避免大模块
- **依赖优化**：减少不必要的依赖，避免循环依赖

**问题6：Bazel的远程缓存如何配置和使用？**

**回答策略：**
- **配置方法**：在.bazelrc中配置远程缓存服务器
- **缓存策略**：设置上传和下载策略
- **性能收益**：显著减少重复构建时间
- **团队协作**：团队成员共享构建缓存
- **注意事项**：缓存一致性、网络带宽、存储成本

## 实战案例分析

### 案例1：大型Android应用构建优化

**场景描述：**
某大型电商应用构建时间超过30分钟，影响开发效率

**分析思路：**
1. **构建分析**：使用Bazel analyze-profile分析构建瓶颈
2. **依赖分析**：检查依赖关系，发现重复依赖和过度依赖
3. **模块拆分**：分析模块粒度，发现模块过大问题

**解决方案：**
```python
# 优化前的BUILD文件
android_binary(
    name = "app",
    srcs = glob(["src/**/*.java"]),  # 问题：包含所有源码
    deps = [
        "//third_party:all_libs",   # 问题：依赖过多
    ],
)

# 优化后的BUILD文件
android_binary(
    name = "app",
    srcs = glob(["src/main/**/*.java"]),  # 只包含主模块
    deps = [
        "//feature:checkout",        # 按需依赖
        "//feature:product",
        "//base:core",
    ],
)

# 新增模块定义
android_library(
    name = "checkout",
    srcs = glob(["src/checkout/**/*.java"]),
    deps = ["//base:core"],
)

android_library(
    name = "product", 
    srcs = glob(["src/product/**/*.java"]),
    deps = ["//base:core"],
)
```

**优化效果：**
- 构建时间从30分钟减少到8分钟（减少73%）
- 增量构建时间从5分钟减少到30秒
- 开发效率显著提升

### 案例2：Android系统模块依赖冲突

**场景描述：**
Android系统构建中出现模块依赖冲突，导致构建失败

**分析思路：**
1. **依赖分析**：使用make deps-json分析依赖关系
2. **冲突定位**：发现多个模块对同一库的不同版本依赖
3. **版本管理**：检查库版本兼容性

**解决方案：**
```python
# 冲突的Android.bp文件
cc_library {
    name: "libA",
    srcs: ["a.cpp"],
    shared_libs: ["libcommon"],  # 依赖libcommon v1.0
}

cc_library {
    name: "libB", 
    srcs: ["b.cpp"],
    shared_libs: ["libcommon"],  # 依赖libcommon v2.0
}

# 解决方案：统一版本或使用别名
cc_library {
    name: "libcommon_v1",
    srcs: ["common_v1.cpp"],
    version: "1.0",
}

cc_library {
    name: "libcommon_v2",
    srcs: ["common_v2.cpp"], 
    version: "2.0",
}

# 使用版本特定的依赖
cc_library {
    name: "libA",
    srcs: ["a.cpp"],
    shared_libs: ["libcommon_v1"],
}

cc_library {
    name: "libB",
    srcs: ["b.cpp"],
    shared_libs: ["libcommon_v2"],
}
```

**优化效果：**
- 解决依赖冲突，构建成功
- 建立版本管理规范
- 提高代码可维护性
