## 解决问题

### 1. Video屏AOD偶现卡死问题
- **问题**：8350平台Video屏AOD场景下偶现卡死
- **原因分析**：Video屏无硬件TE信号，驱动错误依赖TE同步导致帧同步异常
- **解决方案**：修正同步源选择，从TE切换为DSI formatter硬件同步
- **效果**：彻底解决偶现卡死问题

### 2. 开机不亮屏低概率复现问题
- **问题**：8250平台开机不亮屏低概率复现
- **原因分析**：副屏reserved-memory区域与正常内存区域存在交叉
- **解决方案**：推动内存配置优化，重新规划内存布局
- **效果**：彻底消除崩溃隐患

### 3. 多机型并行维护成本高问题
- **问题**：不同机型代码重复，维护成本高
- **原因分析**：缺乏统一的架构设计和代码复用机制
- **解决方案**：实现代码解耦与共线，提高代码复用率
- **效果**：显著降低多机型并行维护成本

## 面试官可能考察的方面及解答

### 1. 技术原理类问题

**Q：请解释一下TE信号和DSI formatter硬件同步的区别和适用场景？**

A：TE（Tearing Effect）信号和DSI formatter硬件同步是两种不同的显示同步机制：

1. **TE信号同步**：
   - 原理：显示面板发送TE信号给处理器，表示当前帧显示完成
   - 优点：精确同步，避免画面撕裂
   - 缺点：需要硬件支持，增加硬件成本
   - 适用场景：高刷新率、高画质要求的显示场景

2. **DSI formatter硬件同步**：
   - 原理：通过DSI接口内部的formatter模块实现同步
   - 优点：不需要额外信号线，硬件成本低
   - 缺点：同步精度相对较低
   - 适用场景：对成本敏感、同步要求不极高的场景

在Video屏AOD问题中，我们发现Video屏没有硬件TE信号，但驱动代码仍然依赖TE同步，导致帧同步异常。解决方案是修改同步源选择，使用DSI formatter内部同步机制替代TE信号同步。

**Q：多机型代码共线维护的技术挑战是什么？如何解决？**

A：多机型代码共线维护面临的主要技术挑战包括：

1. **硬件差异**：不同机型使用不同的显示芯片、面板和驱动
2. **功能差异**：不同机型支持不同的显示功能和特性
3. **性能差异**：不同机型的性能水平不同，需要不同的优化策略
4. **版本差异**：不同机型可能运行不同版本的Android系统

解决方案包括：
1. **抽象层设计**：设计硬件抽象层，隔离硬件差异
2. **配置化实现**：通过配置文件而非代码差异实现功能差异
3. **能力探测**：运行时探测硬件能力，动态调整行为
4. **版本适配层**：设计版本适配层，处理系统版本差异

我们的盘古计划正是通过这些技术手段，实现了vendor侧kernel代码解耦和displayfeature解耦共线，显著提高了代码复用率。

### 2. 实现细节类问题

**Q：如何定位和解决Video屏AOD偶现卡死问题？**

A：定位和解决Video屏AOD偶现卡死问题的过程如下：

1. **问题复现**：
   - 通过长时间压力测试和特定场景测试提高复现概率
   - 使用日志和调试工具记录卡死时的系统状态

2. **根因分析**：
   - 分析显示驱动代码，发现依赖TE信号进行帧同步
   - 查阅Video屏规格书，确认该面板不支持硬件TE信号
   - 分析AOD场景下的显示流程，定位到同步异常点

3. **解决方案设计**：
   - 研究DSI接口规范，了解formatter同步机制
   - 设计同步源切换方案，从TE同步切换为formatter同步
   - 评估方案风险，确保不影响其他显示场景

4. **实现和验证**：
   - 修改显示驱动代码，实现同步源动态切换
   - 在AOD场景下强制使用formatter同步
   - 进行全面测试，确保问题解决且无副作用

这个案例展示了硬件特性分析、驱动代码理解和系统级调试的综合能力。

**Q：如何通过内存布局分析解决开机不亮屏问题？**

A：解决开机不亮屏问题的内存布局分析过程：

1. **问题现象分析**：
   - 收集崩溃日志，分析崩溃时的内存状态
   - 使用内存调试工具跟踪内存分配和访问

2. **内存布局审查**：
   - 分析设备树(DTS)中的内存配置
   - 检查reserved-memory区域定义
   - 对比正常内存区域和保留区域的边界

3. **冲突定位**：
   - 发现副屏reserved-memory区域与正常内存区域存在交叉
   - 分析交叉区域的使用场景和访问模式
   - 确定内存冲突是导致崩溃的根本原因

4. **解决方案实施**：
   - 重新规划内存布局，调整reserved-memory区域位置和大小
   - 确保保留区域和正常区域有足够的边界间隔
   - 更新设备树配置和驱动代码

5. **验证和优化**：
   - 进行大量开机测试，验证问题解决
   - 优化内存使用效率，减少内存碎片
   - 建立内存布局检查机制，防止类似问题

这个案例展示了系统级内存管理、硬件配置分析和底层调试的能力。

### 3. 架构设计类问题

**Q：盘古计划的架构设计思路是什么？如何实现代码解耦？**

A：盘古计划的架构设计思路是实现显示系统的模块化和平台化，核心思路包括：

1. **分层架构**：
   - 硬件抽象层：隔离不同硬件平台的差异
   - 核心服务层：提供统一的显示服务接口
   - 应用接口层：为上层应用提供标准API

2. **模块化设计**：
   - 将显示功能拆分为独立模块
   - 定义清晰的模块接口和依赖关系
   - 支持模块的独立开发和测试

3. **配置驱动**：
   - 通过配置文件定义硬件特性和功能差异
   - 运行时加载配置，动态调整行为
   - 减少代码分支，提高可维护性

代码解耦的具体实现：
1. **接口抽象**：定义标准接口，隐藏实现细节
2. **依赖注入**：通过依赖注入实现松耦合
3. **事件驱动**：使用事件机制减少直接依赖
4. **插件架构**：支持功能插件的动态加载

这种架构设计使不同机型的显示系统可以共享大部分代码，只有硬件相关的部分需要单独实现，大大提高了代码复用率和维护效率。
